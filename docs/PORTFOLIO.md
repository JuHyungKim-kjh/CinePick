# CinePick — 포트폴리오 재료

> 진행 중에 그때그때 쌓는 파일이다. 값과 사실만 정확하면 되고, 문장은 `projects.json` 으로 옮길 때 다듬는다.
> 특히 **측정값은 고친 직후가 아니면 영영 알 수 없으므로** 그 자리에서 적는다.

## 개요

영화 정보를 모아 보여주고 취향을 분석해 추천하는 서버 렌더링 웹 서비스.
CGV·롯데시네마·메가박스 세 예매사를 크롤링해 상영작을 모으고 TMDB 로 살을 붙인다.
**예매는 처리하지 않고 각 예매사로 링크만 중계**하며, 실제 예매 여부는 사용자에게 팝업으로 되물어 확정한다.

## 기능

(작성 예정 — 설문·취향 점수 모델, AI 큐레이션, 예매 중계·평점, 고객지원 게시판)

## 트러블슈팅

### 1. 「상영 예정작」 탭이 매 요청 6초 — TMDB 검색 결과를 기억하지 않아 영구히 반복 호출

**증상**

메인에서 「상영 예정작」 탭을 누르면 십몇 초 동안 흰 화면이 떴다. 같은 페이지 안의 탭인데도
기다려야 했고, **새로고침해도 매번 똑같이 느렸다**. 데이터가 DB 에 쌓이면 빨라질 것 같은데
그렇지 않았다.

**원인**

`MovieService.getMoviesForMainPage()` 가 크롤링 제목이 DB 제목과 안 맞을 때마다 **요청 스레드
안에서 TMDB 검색을 동기로** 부른다. 문제는 그 결과를 어디에도 기억하지 않는다는 것이다.
저장되지 않는 경우가 둘이라 같은 제목을 **영구히 매 요청 다시 물어봤다**.

1. TMDB 에 없는 제목(라이브뷰잉·특별상영·재개봉 표기) — 저장할 것이 없으니 다음에도 다시 조회
2. `findByMovieCd()` 로 기존 행을 재사용한 경우 — 그 행의 DB 제목은 크롤링 표기와 다른 채로
   남아 다음 요청에도 `cleanTitle()` 매칭이 또 실패

예정작 탭이 유독 느린 이유는 `seedIfEmpty()` 가 TMDB `now_playing` 만 적재해 **DB 가 현재
상영작 쪽으로 편향**돼 있기 때문이다. 예정작 제목은 거의 전부가 위 경로를 탔다.

곁들여 있던 것 셋:
- `new RestTemplate()` 의 connect·read 타임아웃이 **둘 다 무제한**이었다. TMDB 가 멈추면
  톰캣 요청 스레드가 영원히 붙잡힌다.
- 제목 매칭이 O(N×M) 이중 루프였고, 비교마다 `replaceAll` 이 **정규식을 새로 컴파일**했다.
- 메인 슬라이더 포스터에만 `loading="lazy"` 가 빠져 있어(다른 세 구역에는 있었다) 화면 밖
  수십 장까지 즉시 내려받았다.

**해결**

- `OpenApiService.searchTmdbByTitle()` 에 `ConcurrentHashMap` 캐시. 핵심은 **"TMDB 에 없더라"는
  사실까지 기억**하는 것이다. 결과 종류마다 수명을 다르게 줬다 —
  성공 24시간 / 결과 0건 6시간(크롤링 주기와 같게) / **호출 실패 1분**.
- `SimpleClientHttpRequestFactory` 로 connect 3초 · read 5초 타임아웃.
- 제목 → 영화 인덱스(`Map<String, List<Movie>>`)를 요청당 한 번만 만들어 O(N) 으로.
- `getMoviesForMainPage()` 가 목록과 '지금 상영 중' movieCd 집합을 **함께** 반환해
  `movieRepository.findAll()` 호출을 요청당 3회 → 2회로.
- `cleanTitle()` 의 정규식을 `static final Pattern` 으로.
- 메인 슬라이더 포스터에 `loading="lazy"`.

**측정값 (전 → 후)**

조건: 크롤링 현재상영작 ~105편 · 상영예정작 144편, 워밍업 완료 후, 비로그인, 반복 측정.

두 단계로 고쳤고 **1단계는 완화, 2단계가 해결**이다. 그 차이가 콜드 수치에 그대로 드러난다.

| 시나리오 | 처음 | 1단계(캐시) | 2단계(선처리) |
|---|---|---|---|
| `?tab=now` 웜 TTFB | 0.70s | 0.034s | **0.031s** |
| `?tab=upcoming` 웜 TTFB | **6.45s** | 0.032s | **0.028s** |
| `?tab=upcoming` **콜드** TTFB | 10.41s | 9.90s | **0.028s** |
| 요청당 TMDB 검색 호출(웜) | 45회 | 0회 | **0회** |
| 탭 전환 | 6.45s (서버 왕복) | 6.45s | **0.016s (왕복 없음)** |

1단계(캐시)만으로는 **콜드 9.9초가 그대로 남았다** — 서버를 새로 켤 때마다 누군가 한 명이
그 값을 다 냈다. 2단계에서 매칭을 크롤링 직후 백그라운드로 옮기고 나서야 사라졌다.

부수 효과로 예정작 목록이 99편 → 102편이 됐다. 검색 쿼리를 `UriComponentsBuilder` 로
인코딩하면서, 제목에 특수문자가 들어가 그동안 조용히 매칭에 실패하던 작품 3편이 살아났다.

**검토했다 버린 대안**

- **Spring Cache(`@Cacheable`) 도입** — 기본 구현 `ConcurrentMapCacheManager` 에 **TTL 이 없다.**
  이번 요구의 핵심이 "실패를 기억하되 영원히는 아니게"인데 그 하나를 못 채운다. Caffeine 을
  더해도 `@Cacheable` 로는 **성공과 실패에 서로 다른 수명**을 줄 수 없다(`unless` 는 저장 여부만
  가른다). 의존성을 둘 늘리고 요구는 반만 채우는 셈이라 `ConcurrentHashMap` 을 직접 썼다.
- **크롤링 갱신(6시간) 때 캐시 전부 비우기** — 처음 떠올린 안이지만 버렸다. 갱신이 바꾸는 것은
  제목 목록이지 "제목 → TMDB id" 매핑이 아니다. 전체를 비우면 **6시간마다 그 시점의 첫 방문자
  한 명이 45번의 왕복을 통째로 뒤집어쓴다.** 모두가 겪던 문제를 6시간에 한 명으로 줄일 뿐
  성질은 그대로다. 결과 종류별 TTL 이 맞다.
- **호출 실패도 6시간 기억** — TMDB 일시 장애를 6시간짜리 "없는 영화"로 굳혀 버린다.
  그렇다고 캐시를 안 하면 TMDB 가 죽었을 때 매 요청이 (제목 수 × 5초)를 쌓는다. 1분이 둘 다 막는다.
- **`movie_alias` 별칭 테이블** — 원인 ②를 DB 로 푸는 안. `ddl-auto: update` 에 마이그레이션
  스크립트가 없는 프로젝트라 스키마를 늘리는 것 자체가 위험하고, 별칭의 출처인 크롤링 제목은
  6시간마다 바뀌고 상영이 끝나면 사라진다 — **영구 저장소에 한시적 데이터를 쌓는 모양**이 되고
  청소 책임이 새로 생긴다.
- **요청 스코프 빈(`MovieCatalog`)으로 `findAll()` 을 요청당 1회로** — 서비스 셋이 같은 스냅샷을
  공유하게 하는 안. 시그니처를 안 건드리는 장점이 있지만, 요청 밖(스케줄러·워밍업)에서 부르면
  터지는 실패 모드가 새로 생긴다. `findAll()` 은 병목의 1% 도 안 되는데 위험만 늘어 하지 않았다.
- **`@Transactional` 로 JPA 1차 캐시에 기대기** — 동작하지 않는다. 1차 캐시는 id 단위라
  `findAll()` **쿼리 자체**는 그대로 세 번 나간다.

**2단계에서 한 일**

- **`MainPageCatalog` 신설** — 크롤링이 끝난 직후 `MovieCrawlerScheduler.refresh()` 가 이쪽을 부르고,
  여기서 제목 매칭·TMDB 보충·사이트 링크 갱신을 **전부 끝내 둔다.** 요청은 완성된 목록을 읽기만 한다.
- **스냅샷 복원 경로는 `useTmdb=false`** 로 부른다. 복원의 목적이 "크롤링을 기다리지 않고 문을 여는 것"인데
  여기서 외부 API 수십 번을 기다리면 그 목적이 사라진다. DB 에 없는 영화만 잠시 빠지고(98편 → 곧 99편),
  뒤이어 도는 크롤링이 채운다.
- **탭을 클라이언트 전환으로** — `HomeController` 가 두 목록을 함께 내려보내고 `home.js` 가 화면에서만
  바꾼다. 주소창의 `?tab=` 도 `replaceState` 로 맞춰 새로고침·공유가 그대로 된다.

**2단계에서 부딪힌 것 둘**

- **순환 의존** — `updateSiteLinks` 를 어디에 둬도 고리가 닫혔다
  (`MovieCrawlerScheduler → MainPageCatalog` 이고 `MovieService → MovieCrawlerScheduler`).
  양쪽이 함께 의존하는 `SiteLinkUpdater` 로 빼서 풀었다.
- **숨은 채로 만든 Swiper** — 예정작 탭을 열면 **슬라이더 왼쪽 절반이 비어 있었다.** 숨은 컨테이너에서
  만들면 폭을 0 으로 재는데, 이 슬라이더는 `centeredSlides + loop` 라 복제 슬라이드 위치까지 어긋나고
  `update()` 로도 돌아오지 않는다. 옆의 큐레이션 슬라이더는 그 둘이 없어서 `update()` 만으로 됐던 것이라
  같은 방법을 쓸 수 없었다. **보이는 탭만 먼저 만들고 나머지는 열 때 만드는** 지연 생성으로 해결했다.

**아직 남은 것**: `OpenApiService.initGenres()` 가 `@PostConstruct`(빈 생성 단계에서 외부 API 호출 —
타임아웃으로 최악 8초까지는 묶였다), 포스터가 TMDB `w500` 원본 직접(카드 표시 크기 대비 과대),
`spring.jpa.open-in-view` 미설정(기본 true), `SimpleClientHttpRequestFactory` 는 커넥션 풀이 없어
호출마다 TLS 핸드셰이크(요청 경로에서 TMDB 가 빠져 중요도는 낮아졌다).

### 2. 메인 포스터가 눌리지 않았다

**증상** — 상단 「영화」 목록에서는 포스터를 누르면 상세로 가는데, **메인 상영작 슬라이더만**
카드 아래 작은 "예매하기" 버튼을 정확히 눌러야 했다. 400px 높이 포스터가 죽은 영역이었다.

**원인** — `home.html` 의 포스터 `<img>` 가 어떤 `<a>` 에도 감싸이지 않았다. 메인의 다른 세 구역
(AI 큐레이션·박스오피스·취향 프로필)은 전부 링크였는데 가장 큰 이 슬라이더만 빠져 있었다.

**해결** — 포스터 블록을 `<a>` 로 감쌌다. **`<a>` 를 `.position-relative` 바깥에 둔 것이 요점**이다.
안에 넣으면 `z-index:10` 인 순번 배지가 링크 위를 덮어 배지 영역만 클릭이 죽는다.

**측정값** — 클릭 가능 영역이 카드당 약 165×40px(예매 버튼)에서 약 165×440px(포스터+버튼)로.
포스터 클릭 · 배지 위 클릭 · 드래그(상세로 안 넘어감) 모두 확인.

**버린 대안** — 카드 전체를 `<a>` 로 감싸는 안(`movie/list.html` 방식). `.card-body` 안에 이미
"예매하기" `<a>` 가 있어 **링크 중첩**이 되므로 쓸 수 없었다.

### 3. 모바일에서 예매 버튼이 화면 밖에 있었다

**증상** — 상세페이지의 예매 사이트 카드가 맨 아래에 있는데, 모바일에서는 포스터가 화면 폭
전체를 차지해 세로로 길어진다. "이 영화 어디서 예매하지"로 들어온 사용자가 한참 스크롤해야 했다.

**원인** — 예매 카드와 정보 카드는 `<main>` 의 형제지만 `<main class="container">` 가 flex 도 grid 도
아닌 일반 block 이라 **`order` 가 아예 듣지 않는다.** 게다가 스펙 표가 정보 카드 *안*에 있어,
카드 단위로만 재정렬하면 [포스터+제목+표] 덩어리 전체가 예매보다 위 아니면 아래로만 간다.
표(6행 ≈ 340px)가 예매 위에 남으면 결국 또 스크롤이다.

**해결** — 768px 미만에서만 중간 래퍼(`.detail-card`/`.detail-row`/`.detail-meta`)를
**`display: contents`** 로 투명하게 만들어 네 블록을 `<main>` CSS Grid 의 직접 아이템으로 올리고
`grid-template-areas` 로 자리를 정했다. 포스터는 120px 로 줄여 제목과 가로로 놓는다.
템플릿에는 클래스와 `<div>` 래퍼 둘만 추가했고 **데스크톱 마크업·화면은 그대로**다.

`row-gap: 0` 으로 두고 세로 간격을 각 블록의 margin 에 맡긴 것이 요점이다 — 종영작(ENDED)이라
예매 카드가 렌더되지 않을 때 빈 행이 간격을 남기지 않는다.

**측정값** — 390×844 기준, 예매 버튼 첫 줄(CGV)이 스크롤 0px 위치에서 y≈450px 로 올라와
**세 버튼 모두 첫 화면에 보인다**(이전에는 y≈1100px 이상, 스크롤 필요).
NOW·UPCOMING(D-Day)·ENDED 세 상태와 데스크톱 회귀를 모두 확인했다.

**버린 대안**
- **카드 순서만 바꾸기** — 위 원인대로 스펙 표가 딸려 올라와 효과가 없다.
- **하단 고정(sticky) 예매 바** — 실제 예매 앱들이 쓰는 방식이지만, 요청이 "상단 배치"였다.
- **뱃지를 제목 옆으로 이동** — 데스크톱 배치까지 바뀌어 요청 범위를 벗어난다. 포스터 좌상단에
  둔 채 크기만 줄였다.

### 4. 오류 화면이 아예 없었다 — 그리고 "없는 영화"가 500으로 나가고 있었다

**증상** — 주소를 잘못 치거나 서버가 예외를 던지면 Spring Boot 기본 Whitelabel 페이지가 그대로 떴다.
흰 바탕에 영문 스택 정보만 있고 **돌아갈 링크가 없다.** 더 나쁜 건 없는 영화 주소
(`/movies/detail/99999999`)가 **500 서버 오류**로 표시된 것이다.

**원인** — `templates/error/` 도 `@ExceptionHandler` 도 없었다. 그리고 500의 진짜 원인은 예상과 달랐다:
`MovieService.getMovieDetail()` 의 `movieInfo.has("status_code")` 검사는 **한 번도 실행되지 않았다.**
TMDB 가 없는 id 에 HTTP 404 를 주는데 `RestTemplate` 이 그걸 `HttpClientErrorException` 으로 먼저
던져 버리기 때문이다. 사용자 잘못(없는 주소)인데 서버 잘못으로 보이고, 검색엔진도 없는 페이지를
살아 있는 것으로 취급한다.

**해결** — 화면을 **한 장이 아니라 두 갈래**로 나눴다.

| | 옷 | 이유 |
|---|---|---|
| 4xx (404·403) | 밝은 화면 + **공통 레이아웃 유지** | 서버는 멀쩡하다. 필요한 건 빠져나갈 길이므로 상단 메뉴·footer 를 그대로 둔다 |
| 5xx (500) | 어두운 전면 + **레이아웃 없음** | `layout.html` 은 `PendingReservationAdvice` 가 넣는 값을 참조한다. 서버 상태를 믿을 수 없는데 그것까지 얹으면 **오류 화면이 또 터진다** |

이 갈래는 새 규칙이 아니다. `loading.html` 이 이미 '어두운 전면 + 레이아웃 없음'이고 같은 이유가
주석에 적혀 있다. 결과적으로 **'어두운 전면 = 시스템 상태 화면'** 이 서비스 전체의 규칙이 됐다.

그 밖에: `OpenApiService.getTmdbMovieDetail()` 이 404 를 잡아 null 을 돌려주고
`GlobalExceptionAdvice` 가 `IllegalArgumentException` → 404 로 내린다. 스택트레이스 대신 여섯 글자
참조 코드(`REF 3F8D53`)를 화면과 서버 로그에 함께 남겨, 문의가 들어오면 그 요청을 바로 찾는다.

**측정값** — 404: 500 → **404**(영화 상세). 응답 본문: 스택트레이스 80줄 + 예외 메시지 → **0줄**.
빠져나갈 링크: 0개 → 상단 메뉴·footer·버튼 2개·1:1 문의.

**검토했다 버린 대안**
- **거대한 「404」 숫자** — 가장 흔하고 쉽지만 어느 서비스에 붙여도 똑같고, 무엇보다 **숫자는 사용자가
  알아야 할 정보가 아니다**(개발자용 코드다). 대신 *한 칸이 비어 있는 필름 스트립*을 그리고 숫자는 작은
  라벨로 내렸다.
- **티켓 스텁 모티프** — 영화관답지만 「찢어진 티켓」이 **예매 실패**로 읽힐 소지가 크다. CinePick 은
  예매를 중계만 하므로 그 오해가 비싸다.
- **오류 화면에 추천작 목록** — 500 화면에서 DB 를 또 부르는 것이라, 그 조회가 실패하면 오류 페이지가
  오류를 낸다.
- **`server.error.include-stacktrace: never` 설정만 믿기** — 실제로 안 통했다. devtools 가 개발
  환경에서 이 값을 always 로 되돌려, 404 JSON 응답에 필터 체인 전체가 담긴 80줄짜리 트레이스가 그대로
  나갔다. 설정 대신 `ErrorRefAttributes` 에서 직접 지운다.
- **`accessDeniedPage("/error")`** — 그냥 forward 라서 컨테이너의 `error.status_code` 가 비고,
  그러면 403 인데 **500 화면**이 뜬다. `sendError(403)` 로 바꿔야 상태가 제대로 실린다.
